## Executive summary

Three things dominate this branch and should be read before the finding list:

1. **The branch does not boot.** `src/admin/mod.rs` registers ~7 identical `POST` routes twice on the same axum `Router`, which panics *during startup* while building the admin router — before any listener binds. 100% reproducible, no attacker needed. The data plane never comes up. (Finding C1.)

2. **The branch does not build in CI/Docker.** The request-path `algorithms` crate depends on `lynxx-algo` via an **absolute path into a developer's `~/Downloads`** (`crates/algorithms/Cargo.toml:8`), with a `build.rs` that compiles and *executes* C at build time. It is unpinned, unchecksummed, outside version control, and absent from any other machine. This is both a reproducibility blocker and a build-time-RCE / supply-chain vector. (Findings C2 / H3.)

3. **`panic = "abort"` amplifies every reachable panic into a full-process crash.** `Cargo.toml:322` sets `panic = "abort"` for release, so tower/axum per-request `catch_unwind` isolation does **not** apply to the shipped binary. Several findings that would be "a 500" under unwinding are instead whole-gateway DoS (rate-limit float panic H1, admin UTF-8 slice M3). A panic-hook comment at `src/main.rs:281` asserts "the gateway hot path has zero remaining panic surface (audit, 2026-05-18)" — that claim is now false.

**Reachability is the key lens.** ~37k lines of new `src/proxy/*` modules are registered as `pub mod` but have **no production callers** — they are staged scaffolding. Most proxy findings are therefore *latent*: real defects that become exploitable the moment the module is wired in, but not reachable from internet traffic today. The genuinely *live* issues are concentrated in **quota enforcement, the rate-limit plugin, the load balancer, the admin API, and the build/supply-chain**. Each finding below states its own reachability.

**Net recommendation:** C1 and C2 are hard release blockers — fix before anything else. Then H1/H2 (live remote-DoS and quota bypass) and the supply-chain pins (H3/H4). The large body of latent proxy findings should be fixed *before* the corresponding modules are wired into the request path; track them so wiring a module is gated on clearing its landmines.

### C2. Core request-path algorithm crate (with build.rs + C compilation) sourced from a developer's ~/Downloads dir, unpinned and unchecksummed

- **Severity:** CRITICAL | **Category:** supply-chain | **Unit:** `supply-chain-build`
- **Location:** `crates/algorithms/Cargo.toml:8`

**What:** The gateway binary takes a NON-optional dependency on the new `algorithms` crate (Cargo.toml:83, `algorithms = { path = "crates/algorithms" }`), and `algorithms` in turn depends on `lynxx-algo = { path = "/Users/shreyansh/Downloads/nginx-master/nginx-algo" }` (crates/algorithms/Cargo.toml:8). Per the root Cargo.toml comment (lines 80-82) this crate is the algorithm dispatch layer: "every adapter compiles in, and the subscription Tier ... selects which one runs at startup" — i.e. load-balancer pick, rate-limit, hashing, URI normalization, etc. all run through it on the request path. In Cargo.lock the `lynxx-algo` v0.2.0 entry (line 2947) has NO `source` and NO `checksum` line, so it is a pure local path dependency with zero integrity pinning. The on-disk crate at that path contains a `build.rs` and a `cc` build-dependency (Cargo.lock lines 2949-2953: `cc`, `crc32fast`, `memchr`), meaning it executes a build script and compiles native C at build time.

**Impact / reachability:** The security-sensitive, request-path algorithm code AND a build-time C compilation step are sourced from an uncommitted, unversioned directory in a single developer's Downloads folder, outside the repo and outside any VCS the gateway controls. The lockfile cannot detect tampering (no checksum). Anyone (or any process) that can write to ~/Downloads/nginx-master/nginx-algo on a build/release host silently controls both the compiled-in algorithms and arbitrary build-time code execution (build.rs runs with the builder's privileges) in the production gateway binary — a full supply-chain compromise vector with no audit trail. It also makes the branch unbuildable in CI/Docker (the path does not exist there), so the release artifact's provenance cannot be reproduced.

**Fix:** Vendor `lynxx-algo` into the repo (e.g. crates/lynxx-algo as a real workspace member) or publish it to a registry / pin it as a git dependency with an explicit `rev = "<sha>"` so Cargo.lock records a verifiable source+checksum. Never reference absolute paths outside the repo. Verify the build.rs/C source is reviewed and reproducible in CI.

**What:** crates/algorithms/Cargo.toml declares `lynxx-algo = { path = "/Users/shreyansh/Downloads/nginx-master/nginx-algo" }` — an absolute filesystem path pointing OUTSIDE the repository, into a developer's personal Downloads directory. The `algorithms` crate is an unconditional dependency of the production gateway binary (workspace root Cargo.toml line 83: `algorithms = { path = "crates/algorithms" }`, commented "every adapter compiles in"), and the shipped adapters call into this dependency on traffic-handling hot paths (e.g. crates/algorithms/src/backbone/adapters/base64_codec.rs, uri_codec.rs, checksummer.rs, hasher.rs, rate_limiter.rs, huffman_codec.rs all call `lynxx_algo::*` for base64 decode, URI escape/unescape, CRC32, hashing, rate-limit admission, and Huffman decode). The referenced crate (verified on disk at that path) has `[build-dependencies] cc = "1"` and a `build.rs`, i.e. it compiles C and runs an arbitrary build script at `cargo build` time. Unlike the sibling `utilx` dependency — which is declared as a canonical `git` source with a `[patch."https://..."]` redirect (workspace root Cargo.toml lines 348-349) for local dev — `lynxx-algo` has NO git/registry source and NO `[patch]` entry anywhere; the absolute local path is authoritative.

(1) Non-reproducible/non-portable: the build silently uses whatever happens to live at that absolute path; CI or any other machine without it cannot build (no patch/fallback to override it, unlike utilx). (2) Tamper surface: an attacker (or accidental edit/malware) that modifies files under ~/Downloads/nginx-master/nginx-algo can inject arbitrary C, arbitrary build-script code (RCE at build time), or subtly broken decode/parse/rate-limit logic into the production proxy without touching the repo, with no checksum to detect it. The TOCTOU between "reviewed repo" and "what actually compiled" is unbounded.

Never reference an absolute path outside the repo tree (especially a user Downloads dir) for a dependency that compiles into the gateway. If a local dev override is desired, express it as a `[patch]` that can be dropped in CI, and keep a canonical pinned source as the default.

### H2. Worker panic (remote DoS) via Duration::from_secs_f64 on inf/NaN/negative when token_rate/leak_rate or window is 0

- **Severity:** HIGH _(reporter: medium)_ | **Category:** dos | **Unit:** `proxy-ratelimit`
- **Location:** `src/proxy/rate_limit.rs:669, 719, 783`

**What:** In the Deny branches, the retry-after delay is computed by float division and fed straight into Duration::from_secs_f64 with no finiteness/sign guard. check_token_bucket (line 667-669): `let wait = (1.0 - entry.tokens) / rate;` then `Duration::from_secs_f64(wait)`. If `rate (token_rate) == 0.0` then `wait = 1.0/0.0 = +inf`; Duration::from_secs_f64(inf) PANICS ('cannot convert float seconds to Duration: value is either too big or NaN'). check_leaky_bucket has the identical pattern at line 781/783 with `leak_rate`. check_sliding_window (line 717-719) and the window math divide by `window_secs = self.config.window.as_secs_f64()`; if `window == Duration::ZERO` then `window_secs == 0.0`, the fraction becomes NaN, and `Duration::from_secs_f64(retry_secs.max(0.001))` can receive NaN (NaN.max(0.001)==0.001 actually, but `elapsed_in_window / window_secs` NaN propagates into `weighted`, breaking the limit comparison). A negative `token_rate`/`leak_rate` likewise makes `wait` negative -> from_secs_f64(-x) PANICS ('value is negative'). The engine (RateLimiter::new / RateLimiterConfig) is a public API and performs NO validation or clamping of token_rate, leak_rate, or window.

**Impact / reachability:** With a plausible operator misconfiguration (`requests_per_second: 0` or negative on the rate-limit plugin), an attacker crashes the request-handling task by simply exceeding the (tiny) burst once. Because the plugin instance is shared (Arc<dyn Plugin>) across all requests, every subsequent rate-limited request re-hits the panic. The panic is fully reachable from untrusted traffic. This is fail-broken behavior in a path whose job is to absorb floods.

**Fix:** Sanitize inputs in the engine, not just the caller: in RateLimiter::new (or each check_* function) reject/replace non-positive `token_rate`/`leak_rate` and zero `window` with safe defaults, and guard the conversion, e.g. `let wait = if rate > 0.0 { ((1.0 - entry.tokens) / rate).clamp(0.0, MAX) } else { FALLBACK };` and use `Duration::try_from_secs_f64(wait).unwrap_or(Duration::ZERO)` (or clamp to a finite ceiling) so a bad config can never panic. Validate window_secs > 0 before dividing.

### H3. PerThread >128-thread fallback under-enforces quota (enforcement bypass on high-core hosts)

- **Severity:** HIGH | **Category:** security | **Unit:** `quota`
- **Location:** `src/quota/mod.rs:418-421, 363-399, 502-529`

**What:** The production-active strategy is PerThread (COUNTER_STRATEGY default = PerThread at line 77; set_counter_strategy has no runtime caller anywhere in the tree). In PerThread mode the running total used for enforcement is `self.calls` (the period BASELINE, only changed at load()/rollover) plus `aggregate_per_thread_calls()` (the live sum of the per-thread slots). flush() deliberately does NOT fold the live aggregate back into self.calls. When a worker thread cannot obtain a slot because all MAX_THREAD_SLOTS (128) are taken, check_and_count_per_thread() falls back to check_and_count_batched() (line 420). The batched path computes `post_total = self.calls.load() + batch_n` (lines 369/374) — i.e. baseline + only this thread's local batch. ### M1. decode_base64_fast / decode_base64url_fast write to dst with no capacity check (OOB write)

- **Severity:** MEDIUM _(reporter: high)_ | **Category:** memory-safety | **Unit:** `algo-http-codec-encode`
- **Location:** `crates/algorithms/src/goals/optimized/base64_decode.rs:122-198`

**What:** decode_internal_fast decodes 3 output bytes per 4 input bytes and writes every output byte through raw pointers (`*dst_ptr.add(d) = ...`) inside the `unsafe` block (lines 139-141, 153-155, 172-174, 187, 195) without ever comparing `d` against `dst.len()`. `dst_len` is never read. The only length validation is on `src` (terminator/`%4==1`). The decoded length is `floor(src_effective_len*3/4)`; if a caller passes a `dst` shorter than that, the writes run past the end of the destination buffer. This is a classic OOB write. Notably the sibling decoder `huff_decode_fast` was explicitly hardened in this same branch to gate every write on remaining `dst` capacity (see huffman_codec.rs comment), but base64 was left trusting the caller.
